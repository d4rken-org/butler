## Context

The editor-v3 rewrite replaced the chunk engine with a piece table (`PieceTable`, `BlockIndex`/`BlockIndexBuilder`, `BlockOriginalDocument`+`DecodeCache`, `WindowedSearch`, `DocumentBuffer`, byte-level `EditorDataSource` with atomic `commit`). 442 module tests green, on-device smoke passed (byte-exact saves, staleness guard, auto-save + rebase). **Base**: execute after `worktree-editor-v3` merges into local main (fresh worktree off main). If executed before the merge, stack commits directly on `worktree-editor-v3` in its existing worktree.

**Verified facts this plan relies on (sizing pass + Codex code review, 2026-07-05):**
- `TextPosition(offset: Long, line: Int, column: Int)`; ~13 substantive files do line/column math. `column` is a Kotlin `String`/Compose-text-layout index (hard Int ceiling); `line` is a `LazyColumn` item index (`items(count: Int)`, `item.index`, `Map<Int, …>` viewport caches in `ui/editor/text/`) — hard Int ceiling at every UI boundary. `DocumentBuffer.refreshStats` computes lines as Long and truncates via `.toInt()` (wraps on overflow today); `findOffset` rejects `line >= totalLines`. `WindowedSearch` tracks Long internally, emits `.toInt()`.
- `ContentSource.File.canWrite` is dead: declared + equals/hashCode + hardcoded `true` in `FileDataSource.open()`; nothing reads it. `GatewaySwitch.canWrite(path)` exists (GatewaySwitch.kt:179). Existing test gateway mocks (DocumentBufferSaveTest, DocumentBufferMultibyteTest, EditorEngineIntegrationTest, FileDataSourceTest/EncodingTest) stub exists/lookup/file/delete/move but NOT canWrite.
- `EditorEngine.getContentStream()` has ONE production caller (`EditorWorkspace.saveFileAs`, EditorWorkspace.kt:417-445); it materializes the whole document. `saveFileAs` does NOT special-case saving to the CURRENT path. Tests: `EditorEngineContentStreamTest` AND `EditorEngineIntegrationTest`.
- Search consumers: `EditorWorkspaceViewModel.next/previousSearchResult` navigate by list index and REQUIRE ascending, deduplicated match order. The ViewModel reads `workspace.canUndo()` by POLLING inside a combine driven by unrelated flows (EditorWorkspaceViewModel.kt:164) — a flow that isn't in that combine never updates the toolbar.
- `EditorSettings` has NO encoding setting. `EditorArguments.Default` (app-workspace `workspace/contracts/editor/EditorArguments.kt`, @Serializable @Parcelize, `EditorArgumentsSerializationTest`) has `filePath/cursorLine/cursorColumn/scrollToLine/initialContent/suggestedTitle`. `EditorWorkspace.createArguments()` (EditorWorkspace.kt:74) rebuilds arguments for session persistence from path/cursor/scroll ONLY; `switchEngine(filePath)` (EditorWorkspace.kt:330) takes only a path.
- Staleness digests in v3 are captured over LOGICAL (post-BOM) block ranges; BOM bytes are not covered.

## Decisions recorded from review discussion (do not re-litigate)

- **Staleness**: keep block-digest verification sampled, not full-file (full-file hashing at save would read the whole file, defeating lazy open on large files). Phase D states the false-negative contract honestly (see below).
- **Search semantics**: non-overlapping matches (findAll semantics) are the intended, standard-editor behavior; the defects to fix are WINDOW-DEPENDENCE and regex anchor/lookaround incorrectness. If the user instead wants overlapping matches, note before executing — that changes Phase A.
- **Overflow handling (user decision 2026-07-05)**: FULL `line: Long` migration (Phase C) — engine/workspace/contracts carry exact Long line numbers; narrowing happens only at the Compose boundary (`LazyColumn.items(count: Int)` / `item.index`), via saturating conversion. Rationale: makes line-addressed navigation (goToLine, search-jump) exact at any depth NOW, and confines future >2^31-line support to a UI-only change (windowed LazyColumn with a Long base line — explicitly a non-goal here). `column` stays Int regardless (hard Kotlin-String/Compose-text-layout ceiling); a multi-GiB SINGLE line remains bounded by column Int and per-line String materialization in both worlds — offsets are the exact currency there.
- **SAF/root runtime verification**: deferred to a separate session; this plan is core-engine only.
- **CommitContext, compaction trigger, CRLF/CR line semantics, findOffset clamping, isModified checkpoint, no-op edits**: settled, no action.
- **"Never snap by manual byte inspection"** (original v3 rule): deliberately overridden during v3 after the on-device Android/ICU decoder bug; rationale in "Background notes". Current byte-inspection + isolated re-decode design stays.

### Phase A — deterministic search + correct regex semantics

1. **Literal/whole-word: window-independent non-overlapping matches.** `WindowedSearch` carries `lastMatchEnd: Long` across windows; each window's match iteration starts at `max(coreOffset, (lastMatchEnd - padStart))` (clamped ≥ 0, Int-narrowed against window length). Output is EXACTLY `Regex.findAll(wholeDocument)` for these modes — ascending, deduplicated, non-overlapping, independent of window/overlap size. Fixes the cross-window consumption anomaly (self-overlapping needles like "aa" on "aaa" straddling a stride boundary).
2. **Regex: full-document scan under a cap.** Window-local regex can NEVER reproduce whole-document semantics for anchors/lookaround (`^foo` falsely matches at every window start, `bar$` at window ends, lookahead across the boundary is silently missed). So: if `totalCharLength <= REGEX_FULL_SCAN_CAP` (constructor param, default 8 MiB chars ≈ 16 MiB transient), materialize once via the existing read path and run `Regex.findAll` on the whole document — exact semantics including anchors/lookaround, no window logic. Above the cap: fall back to today's windowed scan, log WARN once per search, and document in KDoc that anchors/lookaround and matches longer than the overlap are unreliable on documents above the cap. (This replaces the previously sketched window-doubling mechanism — simpler and correct where it matters.)
3. Tests: property test comparing windowed vs whole-string `findAll` for EXACT equality on literal/whole-word — random content (breaks, multibyte, repeats), self-overlapping needles ("aa" on "aaa"-runs, "abab"), window sizes {8,16,32,64} × overlaps {2,4,8}. Regex: anchor cases (`^`, `$`, multiline flag off/on behavior pinned), lookahead across former window boundaries, long matches — all exact under the cap; over-cap fallback behavior pinned by one test with a tiny cap. Existing suites unchanged.

### Phase B — engine concurrency + encoding determinism polish

1. **`replaceText` single-lock, atomic via ops-first ordering (no bookkeeping snapshot needed).** Extract no-lock `insertInternal`/`deleteInternal` (public methods = `bufferMutex.withLock { *Internal }`). `replaceText` takes the mutex ONCE and reorders work: (a) read deleted text, (b) `table.delete`, (c) `table.insert` — piece-table ops only, NO `commitNewEdit` yet; (d) only after both succeed, run `commitNewEdit(Delete)` then `commitNewEdit(Insert)` (still TWO undo entries — parity, `DocumentBufferReplaceTest` intermediate-undo assertions unchanged). If (c) fails, roll back (b) by re-inserting the deleted text under `NonCancellable` and return failure — undo/redo stacks, memory counters, generations, and the saved checkpoint were never touched, so no snapshot/restore of bookkeeping is needed. (Codex: popping one undo entry cannot restore redo-clear/eviction/checkpoint side effects — avoided entirely by ordering.)
2. **`canUndo`/`canRedo` as StateFlows, threaded to the UI.** Add `val canUndo: StateFlow<Boolean>`/`canRedo` to `DocumentBuffer` (updated in `commitNewEdit`/`undo`/`redo`/`initialize`/`release`); keep `fun canUndo(): Boolean` delegating to `.value`. Thread the flows through `EditorEngine` and into `EditorWorkspace`'s combined editor state so `EditorWorkspaceViewModel` consumes them as combine INPUTS instead of polling `workspace.canUndo()` (today the polled value only refreshes when unrelated flows emit — a real staleness bug in toolbar enablement). Update the ViewModel state fields accordingly.
3. **DecodeCache in-flight dedup**: short mutex protects the LRU map + `inFlight: MutableMap<Int, CompletableDeferred<String>>`; misses register a deferred and load OUTSIDE the lock; completion inserts + evicts under the lock; failures complete exceptionally and deregister (retries possible). `clear()` clears both maps (in-flight loads finish; results discarded). Tests: same-key concurrent gets load once; distinct keys load concurrently (real dispatcher, gate in loader); loader failure then retry; clear during load.
4. **Deterministic U+FFFD on save**: `writeSplice`'s added-run encoding switches from `String.toByteArray(charset)` (platform-dependent replacement) to a configured `CharsetEncoder` with REPLACE actions and explicit `replaceWith`: UTF-8 → `EF BF BD`, UTF-16LE → `FD FF`, UTF-16BE → `FF FD`; charsets that cannot encode U+FFFD (Phase E single-byte set) keep default `?`. Update `DocumentBufferSaveTest` byte assertions; add an explicit lone-surrogate exact-bytes test.

### Phase C — Long line migration (exact line addressing end-to-end)

Chosen scope (user decision): `line` and `totalLines` become `Long` from the engine through workspace state and contracts; narrowing to Int happens ONLY at the Compose boundary via saturation. `column` stays `Int` (hard ceiling: Kotlin String indexing + Compose text layout; a multi-GiB single line is additionally bounded by per-line String materialization — out of scope).

1. **Types**: `TextPosition(offset: Long, line: Long, column: Int)`; `DocumentBuffer.totalLines: StateFlow<Long>`; `EditorEngine.totalLines: StateFlow<Long>`; buffer line APIs take Long (`getTextForLine(line: Long)`, `getTextForRange(startLine: Long, endLine: Long)`, `findOffset(line: Long, column: Int)`); `WindowedSearch.Match.line: Long`. Engine line arithmetic (`pos.line ± 1`, `line < totalLines - 1`, cursor movement, `computeEndPosition`) goes Long — it is pure arithmetic today.
2. **Contracts**: `EditorArguments.Default.cursorLine/scrollToLine: Long?` (JSON round-trip of old Int values decodes fine; update `EditorArgumentsSerializationTest` incl. an old-payload compat case). `EditorWorkspace.createArguments()`/restore paths follow. Gates on `:app-workspace:compileDebugKotlin` + `:app:compileFossDebugKotlin`.
3. **UI boundary rules** (the ONLY narrow points): add `internal fun Long.toIntSaturated(): Int`. `LazyColumn` gets `items(count = totalLines.toIntSaturated())` and maps `item.index.toLong()` back to line numbers; `Map<Int, …>` viewport caches in `ui/editor/text/` re-key to `Long` (cheap, no framework constraint); `GoToLineDialog` parses `toLongOrNull()` and range-checks in Long; `EditorInfoBar`/string formatting print Long. Rule: values may narrow ONLY where a Compose/framework API forces Int, always saturating — grep gate: no unguarded `.toInt()` on line-derived or document-scale values anywhere in the module.
4. **`refreshStats`** stops truncating (`.toInt()` wrap today) — totalLines is exact Long.
5. **Saturation semantics at the boundary** (Codex sentinel note applies to the narrowed values): the LazyColumn count saturates to `Int.MAX_VALUE`; lines beyond it are not scrollable in the current UI (documented; a future windowed-LazyColumn design with a Long base line lifts this without engine changes — explicitly a non-goal here). Engine-level goToLine/search-jump beyond the boundary stays EXACT because cursor resolution (`findOffset(line: Long, …)`) no longer narrows.
6. Tests: fake `OriginalDocument`/`BlockIndex` with synthetic `lineBreakCount` > `Int.MAX_VALUE`: exact Long totalLines, `findPosition`/`findOffset`/search line numbers exact past 2^31, goToLine round-trip at a > 2^31 line at engine level, no negative wraps anywhere; serialization compat; UI conversion clamp unit tests where practical (EditorPositionUtils-level).

Estimated ripple: ~13-16 substantive files in `app-workspace-editor` + `EditorArguments` in `app-workspace` (sizing pass list). Mechanical but broad — this phase gets its own commit and a dedicated regression run of the full ported suites.

### Phase D — sampled staleness verification

1. `BlockIndexBuilder` computes a digest per block during the (already whole-file) scan — SHA-256 truncated to 8 bytes, `LongArray` on `BlockIndex` (2 GiB file = 32K blocks = 256 KiB). No extra I/O at open/rebase; remove `DocumentBuffer.firstBlockHash/lastBlockHash` + `hashBlock` re-reads.
2. **BOM coverage** (Codex: logical-block digests start after `bomSize`, so BOM tampering with same size+mtime is invisible): `checkStaleness` additionally re-reads the first `bomSize` physical bytes and compares against the stored `bomBytes` when a BOM was detected.
3. `checkStaleness` order: size → mtime → BOM bytes → digest verification of first + last + K random interior blocks (default `K = 8`, constructor-injectable `Random` for tests). Cost per save ≤ (K+2) × 64 KiB reads + bomSize.
4. **Honest false-negative contract** (Codex: "repeated saves accumulate coverage" was false): if a sampled check MISSES a same-size/same-mtime interior tamper, the save splices around it and the post-save rebase makes the tampered bytes the NEW baseline — the tamper is silently absorbed, permanently. Per-save catch probability ≈ (K+2)/N blocks. Document exactly this in the KDoc and plan; sampling narrows the window, it does not close it. (Closing it fully = full-file verify at save = rejected trade-off.)
5. Tests: seeded sampler catches an interior tamper when it picks the block; a deliberately-missing sample documents the absorption contract; BOM tamper caught; digest capture verified against recomputation; empty/1-block files.
6. Note: `BlockIndex` gains the digest array in its constructor — tests that construct `BlockIndex` MANUALLY (the >Int.MAX offsets test in `BlockOriginalDocumentTest` builds synthetic blocks) need updating; give the digest parameter a benign default so synthetic indexes stay easy to build.

### Phase E — manual encoding selector (single-byte legacy) + real `canWrite`

Scope: user-invoked "Reopen with encoding…" per document. No global setting, no automatic legacy detection, no multi-byte legacy charsets (Shift-JIS/GBK/Big5 need DBCS-aware block snapping — explicitly out).

1. **Charset allowlist v1**: UTF-8, UTF-16LE, UTF-16BE, ISO-8859-1, windows-1252, US-ASCII. Single-byte charsets are safe with the existing block snap (`else -> 0`: no partial sequences) and get `charToByte` fast paths in Phase G. Central list in the editor module (charset id + display name).
2. **Plumbing**: `EditorArguments.Default.charsetOverride: String? = null` (charset name; update `EditorArgumentsSerializationTest`). `FileDataSource` factory gains `charsetOverride: Charset?`; when set, `open()` skips detection: charset = override; BOM bytes are detected and stripped/preserved only if they match the override's family (UTF-8 BOM ↔ UTF-8, FF FE ↔ UTF-16LE, FE FF ↔ UTF-16BE), otherwise treated as content.
3. **Override lifecycle** (Codex: unspecified): the override lives in the workspace state next to `filePath` and is (a) KEPT across session save/restore — `EditorWorkspace.createArguments()` must include it; (b) KEPT by Save-As — `switchEngine` gains a charset parameter and Save-As forwards the active override; (c) CLEARED when a different file is opened (Open File flow) and on close; (d) VALIDATED on restore against the allowlist — unknown/missing charset names fall back to auto-detection with a WARN log instead of letting `Charset.forName()` throw and break session restore.
4. **UI**: an "Encoding" entry (editor toolbar overflow or file card) showing the active charset, opening a single-select dialog of the allowlist; selection with unsaved changes prompts the existing discard dialog; current encoding surfaced in the file info card. Strings extracted + localized per repo rules.
5. **Save**: unchanged mechanics — Original bytes verbatim, added runs encoded with the active charset (wrong-override mojibake stays byte-safe for untouched regions).
6. **Real `canWrite`**: `FileDataSource.open()` sets `canWrite = gatewaySwitch.canWrite(path)`. `DocumentBuffer.saveFile` order: unmodified no-op success FIRST, then read-only fail-fast with a clear exception (Codex: otherwise opening a read-only file and pressing save yields a pointless error). **Auto-save must not spam**: `EditorWorkspace`'s auto-save loop skips read-only sources (check `ContentSource.File.canWrite` before scheduling/attempting) — otherwise an edited read-only file produces a failing save + error every 30s. Minimal UI: read-only indicator in the file card; save action error-surfaced. **Every existing mocked gateway gains a `canWrite` stub** (DocumentBufferSaveTest, DocumentBufferMultibyteTest, EditorEngineIntegrationTest, FileDataSourceTest, FileDataSourceEncodingTest — they currently stub only exists/lookup/file/delete/move and would break).
7. Tests: ISO-8859-1/windows-1252 fixtures (0x80–0xFF bytes): open with override decodes correctly; edit + save round-trips (untouched bytes verbatim, added text in override charset); reopen-with-encoding at engine level; BOM-mismatch handling; restore with unknown charset name falls back cleanly; read-only open → save fails explicitly, unmodified save stays no-op.

### Phase F — streaming Save-As

1. Extract the piece-walking splice from `DocumentBuffer.writeSplice` into a shared `streamPieces(sink, readOriginal: suspend (physicalOffset: Long) -> Source)`; `writeSplice(context)` delegates with `context::openOriginalSource`.
2. New `suspend fun DocumentBuffer.writeContentTo(sink: BufferedSink): Result<Unit>` — under `bufferMutex`, writes BOM + streams pieces reading originals via `dataSource.openByteSource` (no commit can run concurrently: same mutex).
3. **Same-path guard** (Codex: streaming into the CURRENT file truncates the very source the originals are read from — today's materialize-first accidentally protected this): `EditorWorkspace.saveFileAs(newPath)` routes `newPath == currentPath` through the normal atomic `saveFile()` flow instead of the streaming copy; regression test for save-as-to-self.
4. `EditorEngine.getContentStream()` replaced by `suspend fun writeContentTo(sink: BufferedSink)`; `saveFileAs` pipes `gatewaySwitch.file(newPath, rw).sink().buffer()` into it.
5. Tests: rework `EditorEngineContentStreamTest` and the two `getContentStream` cases in `EditorEngineIntegrationTest` to the push API (byte-exactness incl. BOM + unsaved edits); buffer-level `writeContentTo` output byte-equal to `saveFile` output for the same state; save-as-to-same-path regression.

### Phase G — `charToByteInBlock` hardening

Replace decoder-byte-accounting (same unreliable-on-ICU assumption class fixed in the builder) with structural walking:

1. **UTF-16LE/BE**: `byte = 2 * charOffset`, with the odd-tail EOF exception (a final block of odd byte length decodes its last byte to one replacement char): clamp to `min(2 * charOffset, blockByteLen)`. Delete the decode-walk for these charsets. Equivalence test incl. the odd-tail case.
2. **Single-byte charsets** (Phase E set): `byte = charOffset`.
3. **UTF-8**: structural byte walk — lead-byte length table, UTF-16 char contribution (4-byte sequence → 2 chars, else 1), validating continuation bytes. On the first malformed byte, delimit the malformed run structurally (bytes until the next valid lead/ASCII byte, capped 4 KiB) and decode JUST that slice in isolation (REPLACE) to learn its char count, then continue. Valid files: zero decoder dependence.
4. **Residual assumption** (narrow, documented): a malformed slice decoded in isolation yields the same replacement-char count as within the whole block. Backstops: DecodeCache loader count validation + post-save rebase length check fail loudly.
5. Tests (Codex: naive per-prefix decodes are a WRONG reference — the first byte of a valid `é` decodes to a replacement in isolation): reference = ONE full-block decode; for each code-point boundary c reported by the structural walk, assert `decodeIsolated(bytes[0 until walkByte(c)])` equals the first c chars of the full decode — prefix EQUALITY evaluated only at walk-reported boundaries. Property inputs: valid multibyte at all boundaries, lone continuations, truncated sequences, invalid leads, overlong encodings (`C0 AF`), UTF-8-encoded surrogates (`ED A0 80`), and > U+10FFFF (`F5 …`).

### Phase H — piece storage benchmark (decision gate only)

Flat-list recap: pieces in an `ArrayList` with `LongArray` prefix sums rebuilt O(pieces) per edit; lookups binary-search the prefixes. Coalescing + 16 MiB compaction keep piece counts low. A balanced piece tree (VS Code-style RB tree with subtree aggregates) gives O(log n) but is a substantial component.

1. Benchmark lives OUTSIDE the default test suite (Codex: a "non-gating benchmark test" still runs in `testDebugUnitTest`): a `@Tag("benchmark")`-annotated (or `@Disabled`-by-default) JUnit class plus a documented invocation (`./gradlew :app-workspace-editor:testDebugUnitTest --tests "*PieceStorageBenchmark*"` with the tag filter enabled, or run manually). 100k scattered small edits on a ~5 MiB document; line-lookup and search latency at 1k/10k/50k pieces; piece counts under coalescing.
2. Decision rule presented to the user with numbers: implement the tree only if per-edit latency at ≥10k pieces exceeds ~1 ms or UI jank is plausible. Otherwise keep the flat list (storage is `internal`; a later swap needs no API change).
3. This plan does NOT implement the tree; if the benchmark demands it, that becomes its own plan.

## Background notes (for the record)

**Why v3 originally banned byte-inspection snapping**: (a) charset generality — decoder-driven snapping was meant to work for any charset without encoding per-charset byte structure; (b) the old chunk engine's corruption partly stemmed from hand-rolled boundary heuristics (5% tolerance, EOF-gap absorption), so the plan pushed all boundary decisions onto the decoder; (c) decoders own the definition of malformed input. What broke it: the JDK CharsetDecoder contract ("partial sequences are left unconsumed on underflow") is not honored by Android's ICU decoders, which consume partial sequences into internal state — making byte attribution silently wrong. The replacement design (explicit UTF-8/UTF-16 snap + isolated re-decode of each snapped range, identical to the cache loader's decode) makes the consumer invariant hold by construction on any decoder; its cost is per-charset snap knowledge, which is why non-UTF charsets must be explicitly vetted before joining the Phase E allowlist (single-byte: trivially safe; DBCS: excluded).
